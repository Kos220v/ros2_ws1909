# Уличная GPS-навигация с Nav2 — ROS 2 Jazzy

## 1. Что реализовано и где границы применимости

Целевая платформа из исходного проекта: Ubuntu 24.04 / ROS 2 **Jazzy**, Raspberry Pi 5,
гусеничное дифференциальное шасси, два VESC, BNO086 Qwiic (I²C), NMEA GNSS и 2D YDLIDAR.
Для другого дистрибутива параметры и названия плагинов нужно проверить заново.

Робот получает **упорядоченный список GPS-точек WGS84**, преобразует их в `map`
сервисом `/fromLL` и последовательно выполняет `NavigateToPose`. Nav2 строит путь
между точками, перестраивает его при появлении препятствий и выбирает допустимые
скорости по лидарной карте. Неудачная точка **не пропускается**: миссия прекращается.
Встроены проверка готовности, контроль свежести датчиков, ограничение длины отрезков,
остановка при смене режима и watchdog процесса маршрута.

Это **не дорожный автопилот** и не геозона: нет распознавания проезжей части,
тротуаров, разрешённых участков, светофоров, ям, обрывов, людей по камере.
Без заранее известной карты робот может выбрать любой свободный по лидару объезд,
в том числе за пределами желаемого коридора. Для запрета выезда нужны отдельные
геозоны/keepout costmap filters и проверенная карта. На дорогах общего пользования
данную конфигурацию применять нельзя. Первый запуск — огороженная ровная площадка,
наблюдающий оператор и независимая аппаратная аварийная остановка.

**Перед движением обязательно измерить/настроить:**

1. Габариты и центр `base_link`; footprint и зону Collision Monitor.
2. Положение/ориентацию IMU, антенны и лидара в URDF.
3. Абсолютный ENU-курс IMU, магнитное склонение, влияние моторов на магнитометр.
4. Масштаб одометрии, реальные скорости, ускорения и тормозной путь.
5. Модель лидара, UART, дальность, частоту и направления осей скана.
6. Точность и ковариацию GNSS; для узких проходов обычно нужен RTK FIX.
7. Свой маршрут; пример специально заблокирован `enabled: false`.

Здесь выполнены Python/static/unit-проверки. Среда разработки не содержит ROS 2,
Nav2 и оборудования: colcon-сборка, lifecycle, TF на живых данных, проходимость
и торможение должны быть проверены на роботе. Конфигурация — исходный профиль
для настройки, а не подтверждение безопасной автономной эксплуатации.

## 2. Архитектура и файлы

```text
/kolesa/track_left + /kolesa/track_right + /imu/data
     └─> counter_odometry ─> /odometry/local; TF odom→base_link
                    │             └─> /odometry/healthy (для navigation_guard)
                    └─ vx ─> ekf_global <─ /imu/data + /odometry/gps
                                  └─> /odometry/global; TF map→odom
/gps/fix + /imu/data + /odometry/global ─> navsat_transform
                                              └─> /fromLL
WGS84 YAML ─> gps_route ─> NavigateToPose ─> BT ─> planner + controller
/scan ─────────────────────────────────────────> costmaps + Collision Monitor
```

Единственная цепочка автономной скорости (везде `geometry_msgs/msg/Twist`):

```text
controller_server / behavior_server
  → /cmd_vel/nav2_raw
  → velocity_smoother → /cmd_vel/smoothed
  → collision_monitor → /cmd_vel/checked
  → navigation_guard → /cmd_vel/auto
  → cmd_switcher → /cmd_vel → kolesa_control → VESC
```

Не публикуйте команды напрямую в `/cmd_vel` и `/cmd_vel/auto`: это обход защиты.
Не запускайте второй mux, исполнитель маршрута или другой Nav2 action-клиент
параллельно. Это ROS-граф доверенных узлов, а не защищённый канал управления.

| Файл | Назначение |
|---|---|
| `src/project_start/launch/start.launch.py` | Драйверы, URDF/TF датчиков, пульт, mux |
| `src/project_start/launch/localization.launch.py` | counter_odometry, глобальный EKF и navsat_transform |
| `src/project_start/config/localization.yaml` | Настройка локализации |
| `src/bno086_imu/config/imu.yaml` | I²C, частоты, качество BNO086 и склонение |
| `src/project_start/launch/navigation.launch.py` | Nav2, lifecycle manager, защитный gate |
| `src/project_start/config/nav2.yaml` | Параметры всех используемых компонентов Nav2 |
| `src/project_start/behavior_trees/gps_navigation.xml` | Перепланирование и ограниченные recovery |
| `src/project_start/project_start/gps_route.py` | GPS-миссия, отмена и watchdog разрешения движения |
| `src/project_start/config/route.example.yaml` | Заблокированный образец маршрута |
| `src/cmd_switcher/cmd_switcher/policy.py` | Проверяемые правила выбора источника команд |

Ссылка на отсутствовавший `robot_odom` удалена. Локальный EKF заменён узлом
`counter_odometry`: X/Y считаются по приращениям аппаратных счётчиков и BNO086,
а не повторным интегрированием скорости. Подробнее: [ODOMETRY_RU.md](ODOMETRY_RU.md). Старые аргументы
`odom_publish_tf`, `odom_yaw_mode`, `imu_yaw_offset_deg` больше не используются.
Старую индивидуальную поправку `-48°` нельзя автоматически переносить: физический
монтаж задаётся URDF, ноль географического курса проверяется отдельно.

## 3. Установка и сборка

Предполагается уже установленный ROS 2 Jazzy и настроенные UART Raspberry Pi.

```bash
source /opt/ros/jazzy/setup.bash
sudo apt update
sudo apt install ros-jazzy-navigation2 ros-jazzy-nav2-bringup \
  ros-jazzy-robot-localization ros-jazzy-nmea-navsat-driver \
  ros-jazzy-xacro ros-jazzy-robot-state-publisher ros-jazzy-rviz2 \
  python3-colcon-common-extensions python3-rosdep python3-yaml python3-serial python3-smbus2 python3-numpy python3-pytest

# sudo rosdep init     # только если rosdep ещё не инициализирован
rosdep update
cd ~/ros2_ws1909
rosdep install --from-paths src --ignore-src -r -y --rosdistro jazzy
colcon build --symlink-install
source install/setup.bash
```

**YDLidar SDK — внешняя зависимость:** CMake драйвера вызывает
`find_package(ydlidar_sdk REQUIRED)`. Если SDK не установлен, сборка остановится.
Установите совместимую с вашим лидаром версию по `src/ydlidar_ros2_driver/README.md`
и инструкции производителя (https://github.com/YDLIDAR/YDLidar-SDK), затем повторите
сборку. `rosdep` не гарантирует установку этого внешнего SDK.

Пользователь должен иметь доступ к портам (`dialout`, затем повторный вход):

```bash
sudo usermod -aG dialout "$USER"
ls -l /dev/ttyAMA* /dev/ttyUSB*
```

Не запускайте ROS через sudo. Для USB предпочтительны постоянные udev-имена.
По умолчанию ELRS=/dev/ttyAMA0, GNSS=AMA2, левый VESC=AMA3,
правый VESC=AMA4, лидар=/dev/ttyUSB0. IMU: `/dev/i2c-1`, адрес 0x4B (75).
Порты ELRS/VESC заданы в start.launch.py; GPS/лидар и номер шины/адрес IMU
можно переопределять launch-аргументами. Настройка I²C и права группы i2c
описаны в [инструкции BNO086](BNO086_RASPBERRY_PI5_RU.md).
В каждом терминале загружайте оба `setup.bash`.

## 4. TF, IMU, одометрия и GNSS — настроить до Nav2

### 4.1. Дерево TF

```text
map                         ekf_global (динамический)
 └─ odom                    counter_odometry (динамический)
     └─ base_link
         ├─ imu_link        robot_state_publisher, URDF
         ├─ gps_link        robot_state_publisher, URDF
         └─ laser_frame     robot_state_publisher, URDF
```

Ровно **один** издатель на каждое ребро. Не добавлять статический `map→odom`,
не запускать AMCL одновременно с глобальным EKF, не публиковать `odom→base_link`
из VESC или стороннего интегратора. `map` может корректироваться GPS; `odom`
должен оставаться непрерывным для локального управления.

В `tracked_robot.urdf.xacro` измерьте `imu_xyz`, `imu_rpy`, `gps_xyz`, `laser_xyz`.
Оси: X вперёд, Y влево, Z вверх; углы в URDF **радианы**, расстояния метры.
TF антенны нужен для компенсации смещения GPS относительно центра робота.
Лидарная высота 0.55 м в исходном URDF — не подтверждённое измерение.

### 4.2. Абсолютный курс IMU

Для GPS недостаточно гироскопа с произвольным нулём при включении. Quaternion
`/imu/data` должен описывать абсолютную ориентацию в ENU:

- восток: yaw ≈ 0;
- север: yaw ≈ +π/2;
- запад: yaw ≈ ±π;
- юг: yaw ≈ −π/2;
- поворот влево: `angular_velocity.z > 0`.

Драйвер `bno086_imu` использует **Rotation Vector (0x05)** — fusion
акселерометра, гироскопа и магнитометра. Game Rotation Vector не используется:
он не даёт абсолютного курса для GPS. Вход SH-2 — quaternion `(i,j,k,real)`
в магнитной ENU; выход `/imu/data` — `(x,y,z,w)` в истинной ENU.
Проверить на реальной плате все четыре направления обязательно.

Восточное магнитное склонение `declination_deg` задаётся **только драйверу BNO086**.
Для магнитного ENU-пространства реализовано `yaw_true = yaw_magnetic - D`:
магнитный север при D=+10° имеет истинный ENU yaw +80°. Это вращение мировой
системы, не физического монтажа. В `navsat_transform` оставить
`magnetic_declination_radians: 0.0` и `yaw_offset: 0.0`: повторная поправка
исказит маршрут. При замене старого датчика перезапустить counter_odometry, глобальный EKF и navsat.

Калибровка, параметры I²C, проверка осей и допустимость магнитного окружения
описаны в [BNO086_RASPBERRY_PI5_RU.md](BNO086_RASPBERRY_PI5_RU.md).
BNO086 не устраняет помехи VESC/стальных элементов: испытать курс с включёнными
приводами и лидаром. При постоянном искажении поля нужна другая установка IMU
или двухантенный GNSS heading. Не обнулять yaw относительно старта для GPS.

Проверка параметров: `ros2 param get /imu/bno086_imu min_accuracy`.
Без свежих accel/gyro/Rotation Vector и достаточного статуса точности драйвер
не публикует `/imu/data`, а существующий navigation guard блокирует AUTO.
Ускорение включает гравитацию, но в текущих EKF оно **не включено в fusion**;
используются только yaw и wz. Дополнительный AHRS/Madgwick поверх BNO086 не нужен.

### 4.3. Локальная одометрия и глобальный EKF

Локальную `/odometry/local` и **единственный** TF `odom→base_link` публикует
`counter_odometry`. На общей временной шкале интерполируются независимые счётчики
левой/правой гусениц и yaw BNO086. Для каждого малого участка используются
приращение пути и точная формула дуги. По RPM, заданной скорости, duty и ускорению
положение не интегрируется. Старый `ekf_local` больше не запускается.

[Подробная математика, калибровка и отказы — ODOMETRY_RU.md](ODOMETRY_RU.md).
Это плоская модель; боковое проскальзывание физически не наблюдается двумя
тахометрами и одной IMU. Ковариация растёт при движении/повороте, при потере данных
узел останавливает расчёт и переводит `/odometry/healthy` в false.

Глобальный `ekf_global` сохраняет `world_frame: map`, `two_d_mode: true`, 30 Гц,
`sensor_timeout: 0.3`. Его входы:

- `odom0: /odometry/local`: **только vx**, индекс 6; X/Y/yaw локальной позы не
  фьюзятся дополнительно с теми же исходными датчиками.
- `imu0: /imu/data`: абсолютный yaw (индекс 5) и wz (11),
  `relative=false`, `differential=false`; TF монтажа обязателен.
- `odom1: /odometry/gps`: только X/Y (0,1), `relative=false`, `differential=false`.

Порядок 15 флагов robot_localization: `x y z roll pitch yaw vx vy vz vroll vpitch vyaw ax ay az`.
Глобальный EKF по-прежнему предсказывает состояние между GPS-измерениями;
мы не заявляем, что вся навигация теперь обходится без интегрирования/дрейфа.
Не включать локальную позу как абсолютную GPS-позицию, не использовать суммарный
путь гусениц как `pose.position.x`. `/odom/vesc` оставлен для диагностики/guard,
а не как второй дублирующий вход скорости EKF.

Для калибровки используются `distance_per_revolution`, `tacho_counts_per_revolution`,
общий `odometry_scale` и новые индивидуальные `left_odometry_scale`,
`right_odometry_scale`. Все параметры привода применяются при запуске.
Готовые числа из проекта — начальная оценка, не результат нового измерения.

### 4.4. navsat_transform и datum

- Получает `/gps/fix`, `/imu/data`, `/odometry/global`; выдаёт `/odometry/gps` и `/fromLL`.
- `delay: 3.0` даёт время появиться исходным данным, но не заменяет readiness.
- `wait_for_datum: false`: datum определяется при старте. Координаты `map` после
  перезапуска могут измениться; маршрут всегда хранится в WGS84 и каждый запуск
  преобразуется заново. Нельзя сохранять `map`-цели между перезапусками EKF.
- `zero_altitude: true`: двумерная навигация. Приёмник всё равно должен давать
  конечную altitude в NavSatFix; в файле маршрута допустима 0.0.
- `use_odometry_yaw: false`: heading берётся из абсолютной IMU, не из траектории GPS.
- `broadcast_utm_transform: false`: дополнительный UTM TF не нужен.
- `publish_filtered_gps: true`: обратная GPS-публикация полезна для диагностики.

Для постоянной карты возможен фиксированный datum (`wait_for_datum`, `datum`),
но менять это нужно вместе с геопривязкой карты. В поставляемом варианте карты нет.
Широта/долгота в градусах WGS84 — не UTM, не пиксели карты и не координаты EPSG:3857.

NMEA-приёмник должен выдавать валидные fixes и осмысленную ковариацию. Настройте
GGA/GST и частоту 5–10 Гц, если поддерживаются; на 1 Гц `gps_timeout=2.0` оставляет
малый запас. `status >= 0` означает наличие решения, **но не гарантирует RTK FIX**.
Guard проверяет заявленную горизонтальную дисперсию, не парсит фирменный статус RTK.
Для строгого допуска RTK добавьте контроль качества конкретного приёмника.
Обычный GPS с ошибкой 3–10 м не обеспечивает движение по узкому тротуару;
увеличить порог guard — значит разрешить худшую локализацию, а не улучшить её.

## 5. Настройка компонентов Nav2

### 5.1. Глобальная и локальная costmap

Статической карты нет: обе карты **rolling**, слои только `obstacle_layer` и
`inflation_layer`. Локальная: `odom`, 8×8 м, 0.1 м/ячейку, обновление 10 Гц.
Глобальная: `map`, 60×60 м, 0.1 м/ячейку, обновление 2 Гц. Публикация 1 Гц.
Частоту управления нельзя оценивать по частоте визуализации в RViz.

`track_unknown_space: false` делает ещё не обследованные ячейки свободными.
Это позволяет ехать к GPS-точке дальше дальности лидара, но **не доказывает**
проходимость участка. `allow_unknown: false` у planner не превращает такую карту
в заранее обследованную! Конфигурация предназначена для проверенной площадки.
Если нужна консервативная навигация только по известному пространству, нужны
карта/другая стратегия исследования и соответствующая обработка unknown.

Поставляемый footprint — **пример** прямоугольника 1.0×0.7 м относительно `base_link`,
с padding 0.05 м. Замените вершины в **обеих** costmap на реальный внешний контур
с гусеницами/выступами. `wheel_separation` не является шириной footprint.
Слишком маленький контур даёт столкновения, слишком большой блокирует проходы.

`obstacle_layer.scan`:

| Настройка | Значение и смысл |
|---|---|
| `topic: /scan`, `data_type: LaserScan` | Исходный лидар, SensorData QoS; `/scan_reliable` не нужен Nav2 |
| `marking: true` | Конечные лучи отмечают препятствия |
| `clearing: true` | Свободные лучи очищают ранее отмеченные ячейки |
| `obstacle_max_range: 8.0` | Дальность нанесения препятствий; проверить на солнце |
| `raytrace_max_range: 10.0` | Дальность очистки; обычно больше obstacle range и не выше надёжной дальности |
| `*_min_range: 0.1` | Отсечение близких невалидных измерений, не маска всего корпуса |
| `inf_is_valid: true` | `+inf` трактуется как отсутствие препятствия до предельной дальности |
| `expected_update_rate: 0.3` | Максимальный ожидаемый интервал **в секундах**, не 0.3 Гц |
| `observation_persistence: 0.0` | Не накапливать старые пакеты сканов |
| `max_obstacle_height: 2.0` | Предел высоты нанесения; 2D лидар от этого не становится 3D |

В драйвере включён `invalid_range_is_inf`. На реальном YDLIDAR надо подтвердить,
что это действительно свободный луч, а не засветка/ошибка датчика. Поток одних
`+inf` программно неотличим здесь от открытого пространства. Guard ловит потерю
потока/пустой scan, но **не гарантирует обнаружение оптического ослепления**.
Луч на высоте лидара не видит низкий бордюр, яму, проволоку или препятствие ниже
плоскости. Для них нужны другие датчики/слои; нельзя компенсировать это inflation.

`inflation_radius: 1.0` создаёт мягкую зону стоимости вокруг препятствия;
`cost_scaling_factor: 3.0` задаёт спад стоимости. Больше scaling — более быстрый спад,
то есть менее широкий эффективный отступ. Увеличивайте radius для более раннего
объезда, но контролируйте возможность проехать между препятствиями.

Глобальная карта конечного размера: исполнитель ограничивает расстояние от
старта до первой точки и каждый следующий отрезок **15 м**. Разбейте длинные
участки на точки 5–10 м; это не делается автоматически, чтобы не скрывать ошибочный
маршрут. Даже близкая цель может стать недостижимой из-за большого объезда:
60×60 м — не карта города. Увеличение карты требует оценки CPU/RAM и изменения
проверок исполнителя. Глобальная карта забывает области за rolling-окном.

### 5.2. planner_server — Navfn

`GridBased.plugin: nav2_navfn_planner::NavfnPlanner`, `use_astar: true`.
Планирует геометрический путь на глобальной карте вокруг отмеченных препятствий.
`expected_planner_frequency: 1.0` — контроль ожидаемой производительности;
реальный запрос перепланирования раз в секунду задаёт BT `RateController`.
`tolerance: 0.5` допускает конец пути около заблокированной цели, а не строго в
её ячейке. Вместе с goal tolerance это означает, что точка посещается с допуском.
Navfn не учитывает кинематику автомобиля; для вращающегося на месте
дифференциального шасси это подходящий исходный выбор.

### 5.3. controller_server — DWB

Работает 15 Гц, получает скорость из `/odometry/local`. DWB перебирает пары
линейной/угловой скорости и прогнозирует локальные траектории на 2 секунды.
Исходные ограничения: 0…0.35 м/с, |w|≤0.6 рад/с; боковое движение и задний ход
запрещены. Выборки `vx_samples=15`, `vy_samples=1`, `vtheta_samples=20`;
увеличение повышает нагрузку, а не всегда качество.

Ускорения x=0.3 м/с², yaw=0.5 рад/с²; торможение x=−0.4, yaw=−0.6.
Подтвердите их измерениями: управление VESC duty не является точным замкнутым
регулятором скорости. Если фактическая скорость значительно отличается от
команды, сначала настройте привод, затем Nav2. Лимит 1 м/с в hardware launch
выше автономного; ручной режим может быть быстрее.

Критерии (`critics`) и веса:

- `ObstacleFootprint` (1): проверка полного многоугольного контура гусеничного
  робота, а не только центра/вписанной окружности; столкновение нельзя
  «перевесить» желанием ехать к цели;
- `PathAlign` (16, forward point 0.2 м): направление по пути;
- `PathDist` (24): близость к глобальному пути;
- `GoalDist` (20): приближение к цели;
- `RotateToGoal` (32): доворачивание в конце;
- `Oscillation`: подавление чередующихся колебаний команд.

Если робот жмётся к препятствиям, сначала проверьте footprint, inflation и
скан, затем веса. Если колеблется — знаки yaw, задержки одометрии, ускорения,
низкую duty-зону и только после этого critics. Повышать все веса сразу бессмысленно.

`SimpleProgressChecker`: требуется сместиться на 0.25 м за 20 с.
Долгое буксование/стояние вызывает recovery, затем провал цели.
`SimpleGoalChecker`: xy≤0.8 м, yaw≤0.5 рад, `stateful: true`.
Для RTK допуск можно уменьшать после испытаний (например, до 0.2–0.4 м), но
обычный GPS меньшим параметром точнее не станет. Не ставьте маршрутные точки
ближе допуска, если важно действительно посетить каждую.
`failure_tolerance: 0.0` не разрешает долго игнорировать ошибки контроллера.

### 5.4. bt_navigator и Behavior Tree

`NavigateToPoseNavigator` обслуживает каждую GPS-точку. В поставляемом XML:

1. `ComputePathToPose` обновляет глобальный путь с частотой 1 Гц.
2. `FollowPath` следует ему, пока планировщик обновляет путь.
3. При сбое планирования/слежения очищается соответствующая costmap и делается
   одна повторная попытка этого действия.
4. Общая recovery — ожидание 2 с, максимум 3 повтора.
5. Если задача не выполнена, action возвращает ошибку; GPS-миссия прекращается.

Заднего хода и слепых разворотов в BT нет. Очистка costmap не означает,
что препятствие физически исчезло: свежий scan должен нанести его снова,
а Collision Monitor остаётся дополнительным барьером.
`bt_loop_duration=10` мс, `default_server_timeout=20` мс,
`wait_for_service_timeout=1000` мс — внутренние тайм-ауты BT, не лимит
длительности поездки. Лимит точки задаёт `gps_route.goal_timeout` (180 с).

### 5.5. behavior_server

Загружены `Spin` и `Wait`; в текущем дереве вызывается только `Wait`.
Costmap/footprint topics указаны отдельно для local/global. Команды поведения
направлены в тот же `/cmd_vel/nav2_raw`, не напрямую к моторам.
Если добавляете spin в BT, убедитесь, что контур при повороте не задевает
препятствия и Collision Monitor покрывает углы корпуса. Backup намеренно
не загружен и не используется.

### 5.6. velocity_smoother

20 Гц, `OPEN_LOOP`, ограничения совпадают с DWB. Сглаживает ступеньки команд
с учётом ускорения; `scale_velocities: true` сохраняет соотношение компонент.
`velocity_timeout: 0.3` прекращает продолжение старой команды.
`OPEN_LOOP` означает опору на предыдущую команду, а не на точное измерение
текущей скорости. После проверки низкозадержанной одометрии можно исследовать
`CLOSED_LOOP`, но плохая/запаздывающая одометрия ухудшает управление.

### 5.7. collision_monitor

Стоит **после** smoother, чтобы экстренный ноль не растягивался сглаживанием.
Получает исходный `/scan`, проверяет остановочный полигон в `base_link`.
Пример зоны: x=±0.85 м, y=±0.60 м, `min_points: 1`, `action_type: stop`.
Один отражённый луч уже останавливает: безопаснее для первичного запуска,
но возможны ложные остановки от шума/самоотражений. Не повышайте `min_points`
вслепую — можно перестать видеть тонкий столб.

`source_timeout: 0.4`: отсутствие свежего источника блокирует движение.
`stop_pub_timeout: 1.0`: после остановки монитор может перестать публиковать нули;
следующий gate имеет собственный timeout и не сохраняет старую скорость.
Публикация `stop_zone` позволяет видеть полигон в RViz.

Размер зоны определяется не только footprint, но и
**v × суммарная задержка + v²/(2 × реальное торможение) + запас**.
Проверьте и вращение: углы корпуса движутся даже при нулевой линейной скорости.
При увеличении скорости пересчитывайте зону. Слишком большая зона остановит
робота до того, как DWB сможет обойти объект: согласуйте её с inflation.
Collision Monitor — программная дополнительная защита, не safety-rated E-stop.

### 5.8. lifecycle_manager

Автоматически configure/activate: planner, controller, behavior, BT,
smoother, collision monitor. `bond_timeout: 4.0` контролирует связь с lifecycle
узлами. Потеря сервера должна деактивировать стек; более быстрый запрет скорости
обеспечивается guard/mux/driver timeouts. `autostart` активирует серверы, но
**не запускает маршрут и не разрешает движение** без AUTO и gps_route.

### 5.9. Какие компоненты намеренно не запущены

- **AMCL / map_server / SLAM:** нет occupancy-карты, глобальная локализация от GNSS.
- **waypoint_follower:** последовательность GPS-точек, FromLL, timeout и abort
  реализованы в `gps_route`; ROS GPS-waypoint API разных версий не требуется.
- **smoother_server:** не обязателен; это сглаживание *пути*, не скорости.
  `velocity_smoother` решает другую задачу.
- **route_server / docking_server:** дорожный граф и стыковка не требуются.
- **keepout/speed filters:** карта запрещённых зон не предоставлена.

Не включайте все узлы «на всякий случай»: у каждого должен быть источник данных
и согласованное место в TF/командной цепочке.

## 6. Дополнительные блокировки и режимы

`navigation_guard` проверяет время получения **и header.stamp**, наличие свежих
TF `map→odom→base_link`, GPS fix/covariance, норму quaternion, валидность скорости
VESC (драйвер выставляет большую ковариацию при потере телеметрии), covariance
глобальной позиции, непустой scan. Пороги в `nav2.yaml`:

| Параметр | Значение |
|---|---:|
| `gps_timeout` | 2.0 с |
| `scan_timeout` | 0.4 с |
| `imu_timeout` | 0.3 с |
| `odom_timeout` (VESC, локальная одометрия, GPS EKF, TF) | 0.4 с |
| `max_gps_stddev` | 1.5 м, отдельно x/y |
| `max_global_stddev` | 2.0 м, отдельно x/y |
| `command_timeout` | 0.3 с |

Ковариация должна быть конечной и положительной; неизвестная GNSS covariance
отклоняется. Проверяются заявленные данные, а не независимая истинность GPS.
Большие скачки с ложно малой ковариацией, дрейф IMU, ошибки firmware и замороженные
измерения с новыми timestamps требуют дополнительных checks/датчиков.
Guard не проверяет RTK-режим и все диагностические коды VESC.

После потери данных в активном AUTO fault защёлкивается: вернуть MANUAL,
устранить причину, проверить готовность, затем AUTO и новый запуск миссии.
Нет автоматического возобновления маршрута после ошибки. При исчезновении
`gps_route` прекращается его `/navigation/mission_enabled` (10 Гц), и разрешение
движения истекает через 0.5 с. Это также закрывает случай зависшего action-сервера.
При потере guard mux прекращает принимать его команды через 0.3 с.
VESC-драйвер имеет собственный `cmd_timeout=0.5` с.

**Режимы `/control_mode` (Int8):**

- `1 MANUAL`: пульт `/cmd_vel/manual`, затем приложение `/cmd_vel/app_manual`.
  Потеря этих источников даёт ноль, а не переход в AUTO.
- `0 AUTO`: только защищённый `/cmd_vel/auto`; приложение ручного управления
  сначала должно запросить MANUAL.
- `2 AVOID`, `3 RETURN_HOME`, неизвестные значения: **стоп**, пока эти отдельные
  режимы не реализованы. Объезд уже работает внутри AUTO через Nav2.

ELRS публикует heartbeat режима 10 Гц; отсутствие heartbeat 0.5 с останавливает mux.
При смене режима сохранённые команды очищаются. По существующей политике ELRS
потеря радиосигнала **сохраняет выбранный режим**, а процесс ELRS продолжает
heartbeat: AUTO может продолжаться без радиосвязи. Это не равнозначно потере
процесса ELRS. Если требуется stop при потере RC в AUTO, дополнительно внедрите
контроль link/failsafe (не принимайте heartbeat режима за доказательство RC-связи).
Независимый аппаратный E-stop обязателен. Ручной режим в этой конфигурации обходит
Collision Monitor: препятствия и скорость контролирует оператор.

## 7. Порядок запуска

### Шаг A — датчики и приводы, только MANUAL

```bash
# declination_deg — пример СИНТАКСИСА; подставьте местное значение вместо 0.0
ros2 launch project_start start.launch.py \
  gps_port:=/dev/ttyAMA2 gps_baud:=115200 \
  imu_i2c_bus:=1 imu_i2c_address:=75 lidar_port:=/dev/ttyUSB0 \
  declination_deg:=0.0 lidar_delay:=10.0
```

Сначала на вывешенных гусеницах проверьте ручной стоп, направления и тайм-ауты.
Не запускайте параллельно `display.launch.py`: второй state publisher может
дублировать TF. Старт оборудования **больше не создаёт /odom**: локальная
одометрия появляется следующим шагом в `/odometry/local`.

### Шаг B — локализация (второй терминал)

```bash
ros2 launch project_start localization.launch.py
# Свой конфиг:
# ros2 launch project_start localization.launch.py localization_params:=/absolute/path/localization.yaml
```

Дождаться устойчивого курса и GNSS. Проверить:

```bash
ros2 topic hz /scan
ros2 topic hz /imu/data
ros2 topic hz /gps/fix
ros2 topic hz /odom/vesc
ros2 topic echo /gps/fix --once
ros2 topic echo /odometry/global --once
ros2 run tf2_ros tf2_echo map base_link
ros2 run tf2_ros tf2_echo base_link laser_frame
ros2 service type /fromLL
# ожидается robot_localization/srv/FromLL
```

Проехать вручную прямой отрезок 5–10 м, сравнить направление/масштаб локальной
и глобальной одометрии с измерением. Если GPS сдвигает робота поперёк движения,
сначала исправить IMU/TF, не запускать Nav2.

### Шаг C — Nav2 (третий терминал)

```bash
ros2 launch project_start navigation.launch.py
# Свой конфиг:
# ros2 launch project_start navigation.launch.py nav2_params:=/absolute/path/nav2.yaml
ros2 lifecycle get /planner_server
ros2 lifecycle get /controller_server
ros2 lifecycle get /bt_navigator
ros2 lifecycle get /collision_monitor
ros2 topic echo /navigation/ready
```

Lifecycle должен быть `active`, readiness — true. Если нет, guard пишет причину:
`waiting for gps`, `invalid GPS fix/covariance`, `stale TF map` и т. п.
`ready=true` не означает, что маршрут уже разрешён или местность безопасна.

В RViz: Fixed Frame `map`; добавить TF, LaserScan `/scan`, карты
`/global_costmap/costmap`, `/local_costmap/costmap`, пути `/plan`, `/local_plan`,
Polygon `/stop_zone`, обе Odometry. Для LaserScan выбрать Best Effort QoS.
Контур препятствия должен совпадать с физическим объектом при движении и повороте.
Кнопка «Nav2 Goal» сама по себе движение не разрешает: нужна миссия/permission.
Не обходите gate для испытания кнопки.

### Шаг D — свой GPS-маршрут (четвёртый терминал)

```bash
cp src/project_start/config/route.example.yaml ~/my_route.yaml
# Отредактировать: реальные безопасные координаты, enabled: true
ros2 run project_start gps_route --ros-args \
  -p route_file:=$HOME/my_route.yaml \
  -p start_timeout:=120.0 -p goal_timeout:=180.0 -p max_leg_m:=15.0
```

Первая точка ≤15 м от текущего робота, следующие отрезки ≤15 м. Лучше 5–10 м
на прямых и дополнительные точки до/после поворотов, не на самом препятствии.
Цели с неверной схемой, NaN/Inf или слишком длинными отрезками отвергаются до
разрешения движения. Не используйте демонстрационные координаты из YAML!
Ориентация в точке вычисляется по входящему отрезку; последняя точка сохраняет
курс последнего отрезка. Это последовательные остановки/довороты, не обещание
непрерывного прохождения всех точек на скорости.

Переключите тумблер ELRS в AUTO. Альтернативный программный запрос режима
передаётся **ELRS**, а не публикуется вторым издателем в `/control_mode`:

```bash
ros2 topic pub --once /control_mode_command std_msgs/msg/Int8 '{data: 0}'
# Немедленный запрос ручного режима (при исправном ELRS-процессе):
ros2 topic pub --once /control_mode_command std_msgs/msg/Int8 '{data: 1}'
```

Физический тумблер может переопределить программный запрос. Не считайте команду
по ROS аппаратной аварийной остановкой. Ctrl+C у gps_route снимает разрешение
и по возможности отменяет текущий goal; при аварийном завершении работает watchdog.
После ошибки/ручного вмешательства маршрут нужно запустить заново с подходящей
первой точкой. Если acceptance action завис/тайм-аут отмены, сначала перевести
в MANUAL и перезапустить/проверить Nav2, затем новую миссию.

## 8. Обязательные приёмочные испытания

1. **Статический стенд:** никто не публикует скорость кроме mux; выключение
   источников команд/процесса ELRS останавливает выход. MANUAL не переходит в AUTO
   при выключении пульта. Проверить аппаратный VESC timeout и физический E-stop.
2. **Курс/TF:** на восток yaw≈0, на север≈π/2; левый поворот положительный;
   перемещение вперёд согласовано с TF и GPS, scan не зеркальный.
3. **Открытая площадка без препятствия:** 2–3 точки по 5 м, сначала уменьшить
   `max_vel_x`, `max_speed_xy`, smoother `max_velocity[0]` до 0.15 м/с.
4. **Объезд:** широкий неподвижный объект, видимый на высоте лидара; проверить
   обе costmap, глобальное перепланирование, минимальный зазор и реальный путь.
5. **Заблокированный проход:** робот останавливается/выдаёт failure, не пытается
   продавить препятствие, не перескакивает к следующей точке.
6. **Отказы:** отключить scan, GNSS, IMU, одну телеметрию VESC; остановить EKF,
   guard, gps_route, Nav2. Замерить время до нуля команды **и физической остановки**.
   При восстановлении датчика после latched fault движение не начинается само.
7. **Ручной перехват:** AUTO→MANUAL отменяет миссию; AUTO обратно не возобновляет
   старый маршрут без нового запуска. Проверить режим RETURN_HOME: здесь это stop.
8. **Плохой GNSS:** NoFix, неизвестная/слишком большая covariance, задержанные
   timestamps должны блокировать автономию. Высокая частота пакетов сама по себе
   не доказывает корректность измерений.
9. **Перезапуск:** холодный старт локализации и новая конверсия маршрута; никаких
   сохранённых целей в прежней системе map.

Запись для анализа (не добавлять rosbag в Git):

```bash
ros2 bag record /tf /tf_static /gps/fix /imu/data /scan /odom/vesc \
  /odometry/local /odometry/global /odometry/gps /cmd_vel /cmd_vel/nav2_raw \
  /cmd_vel/smoothed /cmd_vel/checked /cmd_vel/auto /control_mode \
  /navigation/ready /navigation/mission_enabled /diagnostics
```

Все компьютеры должны иметь согласованное время (chrony/NTP), одинаковый
ROS_DOMAIN_ID и совместимые QoS. Профиль предназначен для настоящего времени:
`use_sim_time=false`; для rosbag/simulation нужно согласованно адаптировать
часы **всех** узлов, а не переключить только один EKF.

## 9. Диагностика

| Симптом | Что проверять |
|---|---|
| `robot_odom not found` | Используется старый install/overlay: пересобрать и source актуальный workspace |
| Нет `/fromLL` или service timeout | navsat_transform, фиксы, абсолютный IMU, TF антенны, `/odometry/global` |
| GPS-точки повернуты на 90° | ENU vs компасный ноль; quaternion firmware, монтаж IMU, двойное склонение |
| Робот «телепортируется» в map | Скачки GNSS, ковариации, магнитные помехи; odom обязан оставаться непрерывным |
| `invalid wheel telemetry` | Оба VESC должны отдавать свежую телеметрию; `/odom/vesc.twist.covariance[0]` |
| Нет движения при active Nav2 | MANUAL? ready? mission heartbeat? latched fault? полигон StopZone? |
| Цель вне costmap / route leg rejected | Более частые GPS-точки; неверные координаты/датум; слишком далеко первая точка |
| Призраки препятствий | clearing, inf_is_valid, реальные значения scan, TF/timestamps, дальность очистки |
| Costmap пуста при видимом объекте | QoS, frame_id, углы/зеркальность лидара, диапазон высоты, засветка |
| DWB не находит trajectory | footprint, inflation, StopZone, динамические ограничения, ошибка осей/одометрии |
| Не заканчивает точку | Допуск меньше шума GNSS, неверный yaw, привод не выполняет малую скорость |
| `Failed to load plugin` | ROS Jazzy и установленные nav2/dwb пакеты; не смешивать конфиги Humble/Kilted |
| CPU перегружен | Измерить частоты; уменьшить размер/разрешение costmap, выборки DWB, RViz/передачу по Wi-Fi |
