# Одометрия гусеничного робота: тахометры VESC + BNO086

## 1. Выбранное решение

Для имеющегося оборудования реализована **синхронизированная плоская одометрия
по приращениям аппаратных счётчиков и абсолютной ориентации IMU**.

- Перемещение: знаковые тахометры левого и правого VESC, не RPM и не команда мотора.
- Поворот: уже fused Rotation Vector BNO086, с корректным TF монтажа и склонением.
- Локальные X/Y: геометрия коротких дуг, а не повторное интегрирование vx таймером EKF.
- Мировая позиция: отдельный глобальный `robot_localization` EKF с GPS.
- Неопределённость: ковариация положения с учётом качества IMU, погрешности пути,
  времени, поворотов и несогласованности тахометров с IMU.
- Отказ: нет экстраполяции через неизвестное движение; ошибка защёлкивается,
  `/odometry/healthy=false`, автономия запрещается.

Это не обещание «одометрии без ошибки». BNO086 не даёт идеально точный географический
курс, а вращение гусениц не равно перемещению по грунту при пробуксовке. Особенно
важно боковое скольжение: оно **не наблюдается** этими датчиками. GPS/RTK нужен для
ограничения глобального дрейфа; для дальнейшего улучшения локальной одометрии
потребуются независимые измерения движения — например, лидарная/визуальная
одометрия. Текущий лидар используется Nav2 для препятствий, не для scan matching.

## 2. Почему нельзя совсем отказаться от накопления приращений

Тахометр даёт расстояние вдоль движения гусеницы, а не координату карты.
Курс показывает направление в момент измерения, а не весь пройденный маршрут.
Нельзя вычислять `x = весь_путь × cos(текущий_yaw)`: после поворота такая формула
повернула бы весь предыдущий путь и робот «перепрыгнул» бы в другое место.

Устранён именно лишний этап `тики → скорость → интегрирование скорости таймером`.
Теперь используется `тики → приращение расстояния → приращение XY по направлению`.
Геометрическое суммирование таких приращений необходимо и для идеально точных
датчиков; дрейф возникает главным образом из-за ошибок измерения/модели, а не
самого наличия суммы.

## 3. Математика

### 3.1. Аппаратные счётчики

`kolesa_control` разворачивает int32-переполнения каждого счётчика в целочисленный
счётчик сессии и корректирует знак установленного двигателя:

```text
ΔN = wrap_int32(N_new − N_previous)
N_session += encoder_sign × ΔN
k_L = distance_per_revolution / tacho_counts_per_revolution
      × odometry_scale × left_odometry_scale
k_R = distance_per_revolution / tacho_counts_per_revolution
      × odometry_scale × right_odometry_scale
s_L = N_session_L × k_L
s_R = N_session_R × k_R
```

Метры вычисляются из полного числа тиков, а не накапливаются как `v × dt`.
Для пройденного суммарного пробега используется **аппаратный** `tachometer_abs`,
а не `abs(tachometer)` и не сумма модулей наблюдённых знаковых разностей: за время
между запросами гусеница могла проехать вперёд и назад с нулевым net displacement.
Суммарный пробег нужен для диагностики, но не для направленного движения XY.

### 3.2. Общая временная шкала

VESC отвечают по двум независимым UART. Нельзя приписать обеим гусеницам время
одного таймера ROS. Новое сообщение `tracked_robot_interfaces/msg/TrackTicks`
содержит header.stamp, session_id, position_ticks, travel_ticks, meters_per_tick,
valid. У каждой гусеницы свой timestamp.

Три буфера содержат `(time, s_L)`, `(time, s_R)` и `(time, unwrapped_yaw, covariance, gyro)`.
Расчёт идёт только до `min(latest_left, latest_right, latest_imu)`, то есть когда
все источники описывают одну временную область. На ней:

1. Интерполируются накопленные значения счётчиков, не мгновенные RPM.
2. Yaw сначала разворачивается через ±π, затем интерполируется.
3. Интервал делится по **всем** внутренним временным точкам IMU и обоих бортов.
4. Через отсутствующий отсчёт можно интерполировать только при допустимом gap;
   экстраполировать вперёд или через длинную паузу запрещено.

Это устраняет ложный поворот/смещение из-за несинхронных UART и лучше описывает
изменяющуюся кривизну, чем одна дуга между редкими публикациями.
Интерполяция предполагает приблизительно постоянные скорость/угловую скорость
между соседними реальными отсчётами; никакой алгоритм не восстановит точно
неизмеренное быстрое движение между ними.

**Временная точность ограничена драйверами.** Для VESC используется время приёма
кадра на Pi; у стандартного GET_VALUES нет используемой здесь синхронизированной
метки измерения. Для BNO086 — время приёма с оценкой report delay, без полной
синхронизации часов SH-2 с ROS. Добавлены `left_time_offset`, `right_time_offset`,
`imu_time_offset`: `effective_stamp = header.stamp + offset`. Компенсировать ими
следует только **измеренную** систематическую задержку, не подгонять траекторию
на глаз. Запас `timestamp_stddev` увеличивает неопределённость.

### 3.3. Перенос ориентации IMU в шасси

Quaternion BNO086 относится к осям платы `imu_link`, а не обязательно `base_link`.
Из URDF берётся статический `base_link→imu_link`:

```text
q_world_base = q_world_sensor × inverse(q_base_sensor)
```

Это важно и при повороте платы на 90°, и при её установке другой стороной.
Гироскоп поворачивается тем же монтажным преобразованием; для небольшого наклона
используется связь body angular velocity с Euler yaw rate. Сама ориентация уже
отфильтрована SH-2; второй Madgwick и интегрирование ускорения не добавляются.
Монтаж должен быть неизменным. Смена TF во время работы — ошибка.

Склонение исправляется **один раз**, в драйвере BNO086. Одометрия использует
истинную ENU: yaw=0 восток, +π/2 север. Начальная точка odom — X=Y=0 в момент
общего временного старта, начальный yaw — измеренное направление, не принудительно
ноль. GPS не сдвигает локальную odom: коррекция находится в `map→odom`.

### 3.4. Дуга вместо приближения по текущему направлению

Для одного синхронного малого интервала:

```text
Δs = (Δs_L + Δs_R) / 2
Δθ = θ_1 − θ_0                  # yaw уже развёрнут через ±π
u = Δθ / 2
sinc(u) = sin(u)/u              # при u≈0 используется устойчивый ряд
Δx = Δs × sinc(u) × cos((θ_0 + θ_1)/2)
Δy = Δs × sinc(u) × sin((θ_0 + θ_1)/2)
x += Δx; y += Δy; yaw = θ_1
```

Формула точна для постоянной кривизны на данном интервале. При прямой `sinc→1`.
При вращении на месте `Δs_L≈−Δs_R`, поэтому `Δs≈0` и нет выдуманной трансляции.
При реверсе `Δs<0`, направление перемещения меняется корректно.

Для гусеничного шасси **не** используется `(Δs_R−Δs_L)/колея` как измеренный поворот:
в повороте гусеницы скользят. Это выражение сравнивается с IMU только как грубый
индикатор несогласованности. Колея и ошибка её оценки могут влиять на этот
индикатор, но не заменяют курс BNO086.

## 4. Ковариация и границы точности

Состояние `[x,y,yaw]` сопровождается полной матрицей 3×3, включая XY/yaw-корреляции.
Для каждой дуги применяется распространение неопределённости по якобианам:

```text
P_new = F P_old Fᵀ + G Q Gᵀ + lateral_noise
```

Новый абсолютный yaw заменяет старое измерение yaw — неопределённость курса не
наращивается как у неограниченного интегрирования гироскопа. При этом вводится
**общая систематическая ошибка курса**: её влияние на XY растёт с удалением
от начала, не усредняется искусственно каждым новым quaternion.

Шум пути включает минимальное разрешение/шум, относительную погрешность калибровки,
неопределённость временной привязки и индикатор
`abs((Δs_R−Δs_L)−колея×Δθ_IMU)`. Отдельно учитывается возможное боковое смещение
при движении и повороте. Повышенная несогласованность увеличивает ковариацию,
но не «исправляет» её умножением координат на магический коэффициент.

Это **настраиваемая приближённая модель ошибок**, а не доказанная точность и не
полный наблюдатель проскальзывания. Корреляции соседних SH-2-оценок и интерполяций
не известны точно. Одновременная одинаковая пробуксовка обоих бортов может не
создать большого индикатора — GNSS/внешняя одометрия всё равно необходимы.
Параметры шума следует определять испытаниями, а не уменьшать ради красивой RViz.

`Odometry.pose.covariance` содержит XY/yaw; z/roll/pitch помечены большой
дисперсией. vx вычисляется как производная **за фактический обработанный интервал**,
wz — из гироскопа BNO086 в системе шасси. Неизмеренная боковая скорость не
объявляется точным нулём. Скорость нужна Nav2, но **не возвращается обратно
в интегратор локального положения**.

## 5. Архитектура и совместимость Nav2

```text
VESC L ─> /kolesa/track_left  ─┐
VESC R ─> /kolesa/track_right ─┼─> counter_odometry ─> /odometry/local
BNO086 ─> /imu/data ──────────┘                  ├─> TF odom→base_link
                                                └─> /odometry/healthy

/odometry/local (только vx) + /imu/data (yaw,wz) + /odometry/gps (x,y)
                      └─> ekf_global ─> /odometry/global; TF map→odom
/gps/fix + /imu/data + /odometry/global ─> navsat_transform ─> /odometry/gps
```

`ekf_local` удалён из запуска/config. Нельзя запускать его параллельно с новым
узлом: получится два издателя одного TF. Глобальный EKF не получает одновременно
локальные X/Y и повторно те же колёсные/IMU-измерения как независимые точные данные.
Его `odom0` — только vx из `/odometry/local`, плюс исходная абсолютная IMU и GPS.
Между GPS-измерениями глобальный EKF по-прежнему предсказывает движение;
счётчиковая одометрия не превращает GNSS-локализацию в систему без дрейфа.

Для Nav2 имена `/odometry/local`, `odom`, `base_link` сохранены; controller/smoother
конфиги не нужно переводить на другой топик. `/odom/vesc` остаётся для диагностики
и проверки VESC в guard, но не дублируется вторым входом скорости глобального EKF.
Новый `/odometry/healthy` обязателен для navigation_guard. При отсутствии этой
ноды или её heartbeat автономия не разрешается.

## 6. Параметры

Все параметры — при запуске, read-only. Конфиг:
`src/project_start/config/localization.yaml`, секция `counter_odometry`.

| Параметр | Начальное значение | Назначение |
|---|---:|---|
| `max_gap` | .15 с | максимальный промежуток между соседними реальными измерениями одного источника |
| `input_timeout` | .25 с | контроль ROS-stamp и времени получения; независим от max_gap |
| `min_update_interval` | .02 с | не публиковать производную по почти нулевому интервалу |
| `max_track_speed` | 2 м/с | граница правдоподобия тахометров, не разрешённая скорость Nav2 |
| `max_yaw_rate` | 2 рад/с | физическая граница gyro и приращения yaw |
| `yaw_jump_tolerance` | .08 рад | запас на шум/коррекцию SH-2 сверх rate×dt |
| `max_tilt` | .35 рад ≈20° | за пределом плоская модель отвергается, а не считается достоверной |
| `track_width` | .48 м | только индикатор несогласованности; согласовать с геометрией |
| `distance_stddev_per_meter` | .03 | исходная относительная погрешность продвижения |
| `distance_noise_floor` | .001 м | минимальный шум движущегося сегмента |
| `lateral_stddev_per_meter` | .03 | неучтённое боковое перемещение на метр |
| `lateral_stddev_per_radian` | .02 м/рад | боковое смещение при развороте |
| `slip_noise_gain` | .3 | увеличение неопределённости при расхождении гусениц и IMU |
| `heading_bias_stddev` | .05 рад | общий неусредняемый bias курса |
| `timestamp_stddev` | .005 с | оценка ошибки временной привязки |
| `left/right/imu_time_offset` | 0 с | постоянная поправка timestamps, диапазон ±.1 с |
| `odom_frame / base_frame` | odom / base_link | согласовать с URDF, Nav2 и EKF |

Ни ковариации, ни предел наклона/скорости не измерены за пользователя.
Если робот работает на более крутом/неровном грунте, просто повысить max_tilt
недостаточно: нужна 3D-модель, корректная проекция измеренного пути и другие тесты.

В `kolesa_control` добавлены `left_odometry_scale` / `right_odometry_scale`.
Они входят в `meters_per_tick` каждого сообщения, поэтому нет второго несогласованного
набора коэффициентов в counter_odometry. У общего hardware launch старый общий
scale остаётся **1.15**; у отдельного стендового launch — 1.0. При измерениях
явно фиксируйте, какой launch и какие значения использованы.

## 7. Калибровка по шагам

1. **Механика:** `base_link` должен быть в принятом центре движения шасси;
   измерить IMU/антенну/лидар относительно него. Смещённый base_link требует
   соответствующей кинематики, не случайной поправки yaw.
2. **Знаки:** при реальном ходе вперёд `position_ticks` обоих бортов растут.
   Не путать `invert_left/right` команд с `encoder_invert_left/right` измерений.
3. **Курс:** проверить четыре географических направления, левый поворот,
   знак склонения и монтаж. Проверять с работающими моторами; несколько градусов
   ошибки курса уже дают заметную боковую ошибку на длинном прямом участке.
4. **Прямая 10–20 м:** измерить расстояние D рулеткой/независимым RTK. Для каждого
   борта `k_measured = D / abs(Δticks)`; новый индивидуальный scale равен старому
   scale × D / опубликованное перемещение этого борта. Несколько повторов
   вперёд и назад на типичном покрытии, с рабочей нагрузкой.
5. **Поворот на месте:** XY не должны выдумывать дугу из ненулевого yaw при
   полусумме бортов≈0. Реальное боковое смещение гусеничного робота на грунте
   возможно — его нельзя убрать подгонкой GPS-точки или занулением ковариации.
6. **Окружность/восьмёрка:** проверить знаки, кривизну, closure error. Сравнить
   асинхронные timestamps и yaw; большие задержки датчиков дают систематическую
   ошибку именно в поворотах. Корректировать time_offset только по измерению.
7. **Оценить шум:** повторные траектории, стоянка, разные покрытия. Увеличивать
   модель неопределённости до реалистичной, не заявлять сантиметровую точность
   по качественному виду одного графика.

На месте гироскоп может иметь небольшой bias. Он не интегрируется повторно
в yaw этой нодой. Медленные магнитные поправки BNO086 остаются свойством входной
ориентации; скачки сверх порога блокируют одометрию, постепенную магнитную ошибку
один BNO086 не способен независимо распознать.

## 8. Сборка, запуск и проверка

Введён новый ROS message-пакет. Собрать весь workspace или зависимости до project_start:

```bash
source /opt/ros/jazzy/setup.bash
cd ~/ros2_ws1909
sudo apt install python3-numpy
rosdep install --from-paths src --ignore-src -r -y --rosdistro jazzy
colcon build --symlink-install --packages-up-to project_start
source install/setup.bash
ros2 interface show tracked_robot_interfaces/msg/TrackTicks
```

Старая среда с ранее установленными launch/config может всё ещё запускать ekf_local.
После пересборки открыть новый терминал и source актуальный `install/setup.bash`.
Сначала остановить старый стек. Первый запуск — **неподвижный робот**, MANUAL,
подтверждённый курс IMU и готовность к аварийному отключению.

```bash
# Терминал 1: локальное склонение вместо 0.0
ros2 launch project_start start.launch.py declination_deg:=0.0
# Терминал 2: запускает counter_odometry + ekf_global + navsat_transform
ros2 launch project_start localization.launch.py
# Терминал 3:
ros2 topic echo /kolesa/track_left --once
ros2 topic echo /kolesa/track_right --once
ros2 topic hz /odometry/local
ros2 topic echo /odometry/healthy
ros2 topic echo /odometry/local --once
ros2 run tf2_ros tf2_echo odom base_link
```

`/odometry/healthy` станет true после первого полностью синхронизированного
интервала. TF/Odometry получают **время измерения**, не искусственное «сейчас».
Частота зависит от обоих UART и IMU; не ждать ровно 30/50 Гц по таймеру.
Дополнительная задержка обычно порядка периода более медленного источника;
проверить, что Nav2 transform_tolerance подходит к фактической задержке.

После проверки локализации запускать Nav2 и GPS-маршрут по основной инструкции.

## 9. Отказы и восстановление

При разрыве данных, недопустимом скачке курса, смене UUID VESC-ноды, изменении
масштаба/монтажа, невалидном timestamp, слишком большом наклоне или fault VESC:

- локальная поза и TF больше не публикуются;
- `/odometry/healthy` становится false, diagnostics содержит причину;
- navigation_guard блокирует автономные скорости;
- нет автоматического продолжения старой траектории после возвращения датчика.

Порядок: остановить физически → MANUAL → устранить причину → на стоянке
перезапустить `localization.launch.py` (при ошибке аппаратного счётчика также
`kolesa_control`/hardware) → проверить курс/health/GPS → заново запустить Nav2 при
необходимости и миссию. Прошлую map/odom-цель не сохранять через reset локализации.
Восстановить точную XY-траекторию через интервал без курса невозможно только
по изменению итоговых счётчиков; поэтому этот код её не придумывает.

Во время потери телеметрии привода есть и отдельная блокировка kolesa_control,
но локальная одометрия сама не управляет моторами. Ручное движение остаётся
ответственностью оператора; аппаратный E-stop и штатный VESC timeout обязательны.

## 10. Что проверено и что ещё нужно проверить на железе

Синтетические тесты: прямая по четырём направлениям, реверс, дуга 90°, поворот на
месте, переменная кривизна, переход ±π, окружность с UART-рассинхронизацией 17 мс
и разными частотами IMU/VESC, PSD/симметрия covariance, пропуски, session reset,
скачки, stale timestamps, монтаж IMU, аппаратное переполнение int32 и повторные
пакеты. Также сохранены проверки GPS-маршрута, mux и протокола BNO086.

```bash
PYTHONPATH=src/project_start:src/kolesa_control:src/bno086_imu:src/cmd_switcher \
  python3 -m pytest -q src/project_start/test/test_counter_odometry.py \
  src/project_start/test/test_odometry_ros_adapter.py \
  src/project_start/test/test_navigation_safety.py src/kolesa_control/test \
  src/bno086_imu/test src/cmd_switcher/test/test_policy.py
```

**В среде разработки нет ROS 2, VESC, BNO086 и физического робота.** Эти тесты
подтверждают математику и обработку искусственных данных, а не реальную точность
в сантиметрах. colcon/генерация интерфейса, реальная временная привязка,
калибровка, торможение и испытания траектории обязательны на оборудовании.

Для анализа записывать:

```bash
ros2 bag record /kolesa/track_left /kolesa/track_right /kolesa/diagnostics \
  /imu/data /imu/accuracy /odometry/local /odometry/healthy \
  /odometry/global /gps/fix /tf /tf_static /diagnostics /cmd_vel
```

Не добавлять rosbag в Git. Оценивать local odom отдельно от GPS-corrected global:
иначе GPS может скрыть систематическую ошибку масштаба или задержки локального расчёта.
