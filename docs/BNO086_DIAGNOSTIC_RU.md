# Стендовая диагностика BNO086: RST, INT, I²C, Product ID

Утилита `bno086_imu.diagnose` **не является ROS-узлом**, не публикует IMU/TF,
не запускает навигацию и не включает отчёты движения. Рабочий драйвер сохраняет
прежнюю защиту INT. Утилита намеренно выполняет диагностический обмен по I²C,
даже если после reset не наблюдался INT LOW.

## Перед запуском

- Робот неподвижен, силовая часть отключена, аппаратный E-stop доступен.
- Завершить hardware/localization/navigation, оба варианта IMU-драйвера,
  `gpioset`, `i2cdetect` и любые другие клиенты этой шины.
- Проводка: 3V3→пин1, GND→пин6, SDA→пин3, SCL→пин5,
  RST→GPIO17/пин11, INT→GPIO27/пин13. Только 3,3 В, PS0/PS1 открыты.
- Права групп `i2c` и `gpio`, см. [инструкцию](BNO086_RASPBERRY_PI5_RU.md).
- Утилита делает аппаратный reset **для каждого адреса**, уничтожая прежнее
  состояние IMU. После теста перезапускать весь стек на стоянке, не продолжать
  старую миссию и не объединять ориентации до/после сброса.

Cooperative flock защищает от второй копии нашего драйвера; сторонние программы
могут игнорировать его. GPIO запрашиваются эксклюзивно. Запуск от root не нужен.

## Запуск из исходников — без colcon и без ROS

```bash
cd ~/ros2_ws
sudo apt install python3-smbus2 python3-libgpiod
set -o pipefail
PYTHONPATH="$PWD/src/bno086_imu" /usr/bin/python3 -u -m bno086_imu.diagnose \
  --confirm-stationary --i2c-bus 1 --gpio-chip auto \
  --rst-gpio 17 --int-gpio 27 \
  2>&1 | tee "$HOME/bno086-diagnostic.log"
```

Параметры по умолчанию проверяют **0x4A, затем 0x4B**, с отдельным сбросом перед
каждой попыткой. Для одного адреса: `--addresses 0x4b`. При необходимости явно
задать подтверждённый путь `--gpio-chip /dev/gpiochip4`. Номер RP1 зависит от ядра;
`auto` ищет label `pinctrl-rp1`, а не угадывает номер.

Альтернативный запуск после сборки пакета:

```bash
colcon build --symlink-install --packages-select bno086_imu
source install/setup.bash
ros2 run bno086_imu bno086_diagnose --confirm-stationary --i2c-bus 1
```

Не передавать `--ros-args`: это обычная CLI, параметры разбирает argparse.

## Последовательность

1. Открывает шину, получает flock, резервирует GPIO, печатает выбранный chip.
2. Читает INT ещё до сброса. Удерживает RST LOW 10 мс, наблюдая INT.
3. Отпускает RST и сразу опрашивает INT в течение 2 с с интервалом около 1 мс.
   Нет слепого ожидания 300 мс после сброса. Linux может задержать поток:
   **короткие импульсы могут быть пропущены**, это не запись фронтов ядром
   и не замена осциллографу/анализатору.
4. Независимо от INT выполняет raw I2C_RDWR чтения SHTP. Не использует SMBus
   регистры или QUICK-сканирование. Вычитывает до 16 стартовых пакетов.
5. Отправляет Product ID request (канал 2, `f9 00`), до 40 раз читает ответ
   в пределах программного окна 2 с. Размер транзакции ограничен 4096 байтами,
   hex больших пакетов в логе обрезается до 96 байт. Ошибки errno и нарушения
   формата печатаются; фрагментированные пакеты не собираются.
6. Успех: ответ на канале 2 с ID `f8` и длиной payload 16 байт; выводятся
   reset cause, версия, software part/build. Это проверка обмена SH-2,
   **не проверка калибровки, монтажа или качества IMU**.
7. Повторяет для второго адреса, печатает JSON `SUMMARY`, освобождает GPIO/I²C.
   При завершении пытается выставить RST HIGH перед освобождением линии;
   электрический уровень после освобождения зависит от подтяжек платы.

Количество операций ограничено, но I²C ioctl может блокироваться до тайм-аута
ядра; программные 2 с не являются жёстким пределом длительности системного вызова.

## Как читать результат

- `INT=0/1` — наблюдённый физический LOW/HIGH, вывод при изменениях.
- `Post-reset INT LOW observed` — наблюдение до первого обмена I²C.
- `SUMMARY.int_low` — был ли LOW после отпускания reset за всю попытку,
  включая последующий обмен.
- `VALID SH-2 Product ID` — проверка структуры ответа пройдена. При INT HIGH
  это повод проверять отдельно линию INT/последовательность запуска, а не
  разрешать навигацию без неё.
- `errno=121` — Linux сообщил Remote I/O error; возможен NACK, но по одному errno
  нельзя отличить неправильный адрес, питание, проводку и timing.
- Только нули/неправильные заголовки — **не** успешная идентификация.
- Отсутствие Product ID **не доказывает**, что плата неисправна: остаются
  ограничения этой диагностической реализации, интерфейса и питания.

Коды выхода: 0 — хотя бы один корректный Product ID; 1 — ни одного;
2 — ошибка аргументов/инициализации/выполнения; 130 — Ctrl+C.
Передать для анализа **весь** `~/bno086-diagnostic.log`, не только SUMMARY.

Проверено офлайн на fake GPIO/I²C, не на реальном BNO086/Pi 5.
